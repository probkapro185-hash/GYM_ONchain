# SFEDU Gym CRM + AI/RAG

Исправленная и усиленная версия CRM спортивного зала на Go, PostgreSQL, Redis и встроенном AI-помощнике с RAG.

## Что входит

- роли `client`, `manager`, `admin` и JWT-аутентификация;
- клиенты, заявки, тренеры и расписание;
- баланс, платежи, магазин, абонементы и заказы;
- PostgreSQL-транзакции для денежных и связанных бизнес-операций;
- AI-чат по CRM с OpenAI Responses API;
- RAG по документам из `knowledge/` через embeddings + PostgreSQL/pgvector;
- история AI-диалогов и сохранённые RAG-источники;
- полноценный адаптивный HTML-интерфейс SFEDU в `frontend/index.html`, который раздаёт сам Go backend;
- AI-помощник встроен прямо в клиентский и staff-кабинет;
- отдельный технический demo AI-чата оставлен в `examples/ai-chat/` для отладки.

## CRM+ расширение

В этой версии основной набор функций спортивного клуба заметно расширен. AI/RAG при этом не менялся.

### Для клиента

- дневник прогресса: вес, процент жира, талия, грудь, бёдра и комментарии;
- история прогресса в личном кабинете;
- центр внутренних уведомлений с непрочитанным счётчиком;
- самостоятельная отмена запланированной тренировки не позднее чем за 2 часа до начала без списания занятия;
- автоматическое отображение замороженного состояния абонемента.

### Для менеджера / администратора

- расширенная CRM-карточка каждого клиента;
- внутренние заметки сотрудников;
- задачи и повторные контакты по клиентам со сроками, просрочкой и списком «Мои задачи»;
- контроль удержания: последний визит, дни без посещений, ближайшее окончание абонемента;
- заморозка и разморозка абонемента с автоматическим переносом даты окончания на фактический срок заморозки;
- ручное продление абонемента;
- продажа товара или абонемента «на стойке» с транзакционной фиксацией в финансовом журнале;
- CSV-экспорт списка клиентов, финансов и полной CRM-карточки клиента.

### Для руководителя

- обзор клуба с активными клиентами и абонементами, тренировками и заявками;
- показатели удержания: клиенты без визитов 14+ дней и абонементы, истекающие в ближайшие 7 дней;
- число открытых follow-up задач;
- поступления и завершённые тренировки за последние 30 дней;
- загрузка тренеров и процент завершения тренировок;
- журнал аудита изменяющих действий сотрудников.

### Надёжность и эксплуатация

- `/healthz` — состояние процесса;
- `/readyz` — готовность PostgreSQL и статус необязательного Redis;
- `/metrics` — Prometheus-compatible HTTP метрики;
- `X-Request-ID` на каждом запросе и в логах;
- audit trail для изменяющих staff/client запросов;
- security headers и Content-Security-Policy;
- frontend разделён на `frontend/index.html`, `frontend/assets/app.css` и `frontend/assets/app.js` вместо одного монолитного HTML.

## Требования

Для запуска через Docker достаточно Docker + Docker Compose. Dockerfile собирает приложение актуальным builder-образом Go 1.26.6, а `go.mod` требует Go 1.25+ из-за актуальных security-hardened зависимостей.

Для запуска без Docker нужны:

- Go 1.25+;
- PostgreSQL 16 с extension `pgvector`;
- Redis 7+ — необязателен, при его недоступности приложение работает без кэша.

## Быстрый запуск

```bash
cp .env.example .env
```

В `.env` обязательно замените:

- `POSTGRES_PASSWORD`;
- `JWT_SECRET` — не менее 32 случайных символов;
- `ADMIN_PASSWORD` — 8–72 байта;
- `OPENAI_API_KEY` — только если нужен AI/RAG;
- для реальной отправки писем: `MAIL_MODE=smtp`, `SMTP_HOST`, `SMTP_USERNAME`, `SMTP_PASSWORD`.

Запуск:

```bash
docker compose up --build -d
docker compose logs -f app
```

После запуска основной сайт доступен сразу по адресу:

```text
http://localhost:8080
```

Отдельно проверить backend можно командой:

```bash
curl http://localhost:8080/healthz
```

Ответ:

```json
{"status":"ok"}
```

Дополнительные operational endpoints:

```text
GET /readyz
GET /metrics
```

Redis не является обязательной зависимостью `app`: если Redis не поднялся, backend отключит кэш и продолжит работать.

## Конфигурация AI

```env
OPENAI_API_KEY=ваш_ключ
OPENAI_BASE_URL=https://api.openai.com/v1
AI_CHAT_MODEL=gpt-5.6
AI_EMBEDDING_MODEL=text-embedding-3-small
AI_KNOWLEDGE_DIR=knowledge
```

API-ключ хранится только на backend. Если `OPENAI_API_KEY` пуст, основная CRM продолжает работать, а AI endpoints возвращают `503`.

`OPENAI_BASE_URL` валидируется как абсолютный `http/https` URL без credentials, query и fragment.

## Активация аккаунта и восстановление пароля

Клиенту больше не задаёт пароль менеджер. Основной flow:

1. клиент оставляет заявку, указывая ФИО, телефон, email и пол;
2. manager/admin одобряет её;
3. backend создаёт заблокированный до активации client account и 256-bit одноразовый token;
4. в БД сохраняется только SHA-256 token, а не сама ссылка;
5. клиент получает письмо со ссылкой `/?action=activate&token=...`;
6. клиент самостоятельно создаёт пароль, после чего account становится активным;
7. token сразу инвалидируется и повторно использовать его нельзя.

Для восстановления пароля кнопка «Забыли пароль?» вызывает `POST /api/v1/auth/forgot-password`. Ответ одинаков для существующего и неизвестного email, чтобы не раскрывать список аккаунтов. Ссылка reset одноразовая, имеет отдельный TTL, а смена пароля увеличивает `token_version`, отзывает старые JWT.

Новые публичные endpoints:

```text
POST /api/v1/auth/activate
POST /api/v1/auth/forgot-password
POST /api/v1/auth/reset-password
```

Staff endpoints:

```text
POST /api/v1/users/invite
POST /api/v1/users/{id}/resend-activation
```

`POST /api/v1/users` доступен только admin и создаёт только сотрудников. Для клиентов обязателен путь приглашения/активации. У старых заявок без пола менеджер выбирает его при одобрении: `POST /api/v1/applications/{id}/approve` принимает `{"gender":"female"}` или `{"gender":"male"}`. У новых заявок значение уже сохранено; пустой объект одобрения сохраняет его.

Заявка на тренировку принимает необязательный `trainer_id`. При одобрении выбранный тренер сохраняется автоматически; менеджер может передать другой `trainer_id` или `clear_trainer: true` для занятия без тренера. Администратор видит всех тренеров через `GET /api/v1/admin/trainers` и может восстановить деактивированную карточку. Публичный `/api/v1/trainers` показывает только активных тренеров.

Email delivery настраивается так:

```env
APP_BASE_URL=http://localhost:8080
ACCOUNT_ACTIVATION_TTL_HOURS=24
PASSWORD_RESET_TTL_MINUTES=60

# Только для локальной разработки: письмо/ссылка выводятся в backend log.
MAIL_MODE=log

# Для настоящих писем:
# MAIL_MODE=smtp
# SMTP_HOST=smtp.gmail.com
# SMTP_PORT=587
# SMTP_USERNAME=sender@gmail.com
# SMTP_PASSWORD=app_password_from_provider
# SMTP_FROM=sender@gmail.com
# SMTP_FROM_NAME=SFEDU Gym
```

`MAIL_MODE=log` предназначен только для локальной разработки. В `APP_ENV=production` приложение требует `MAIL_MODE=smtp`. Для публичного deployment `APP_BASE_URL` должен указывать на адрес, доступный клиентам, а не на `localhost`.

Docker Compose передаёт эти параметры и TTL в контейнер приложения. Фотографии тренеров хранятся в отдельном volume `trainer_uploads`, доступном непривилегированному пользователю приложения, и сохраняются после пересоздания контейнера.

## AI/RAG

База знаний находится в `knowledge/*.md` и `knowledge/*.txt`.

При индексации backend:

1. считает SHA-256 документа;
2. переиндексирует только новые/изменённые файлы;
3. удаляет из pgvector документы, которых больше нет в каталоге;
4. разбивает текст на чанки с overlap без overlap-only дублей;
5. получает embeddings размерности 1536;
6. сохраняет их в `ai_chunks.embedding vector(1536)`;
7. использует HNSW/cosine search для RAG.

Параллельные reindex внутри одного процесса сериализованы mutex-ом.

### AI endpoints

```text
POST   /api/v1/ai/chat
GET    /api/v1/ai/conversations
GET    /api/v1/ai/conversations/{id}
DELETE /api/v1/ai/conversations/{id}
GET    /api/v1/ai/knowledge        # admin
POST   /api/v1/ai/reindex          # admin
```

`POST /api/v1/ai/chat` ограничен 20 запросами в минуту на авторизованного пользователя.

AI получает только разрешённый персональный контекст текущего пользователя. Роль перечитывается из БД, а не доверяется входному JSON. Для OpenAI используется стабильный приватный `safety_identifier`, вычисленный из внутреннего user ID через SHA-256; email и телефон в него не включаются.

Источники RAG сохраняются вместе с ответом ассистента в `ai_messages.sources`, поэтому после повторного открытия диалога они не пропадают.

## Полноценный frontend

Основной интерфейс находится в `frontend/index.html`, а стили/логика вынесены в `frontend/assets/app.css` и `frontend/assets/app.js`. Всё обслуживается самим Go backend. Отдельный web-сервер для сайта не нужен.

Запуск локально:

```bash
go run ./cmd/server
```

После этого откройте:

```text
http://localhost:8080
```

Пользователь входит обычным email/паролем через `/api/v1/auth/login`. JWT сохраняется frontend автоматически и подставляется во все защищённые API-запросы. Поля для ручного ввода Bearer token или Backend URL пользователю не показываются.

Встроенный «ИИ Спортсмен» использует тот же JWT. Frontend отправляет в `POST /api/v1/ai/chat` только `message` и, при продолжении диалога, `conversation_id`; `user_id` не принимается от браузера и определяется backend по авторизации.

Старый небезопасный self-topup клиента удалён из UI: клиент видит информационное окно, а фактическое пополнение выполняет manager/admin через `/api/v1/finance/topup`.

Технический demo чат в `examples/ai-chat/` оставлен только для отладки API и не нужен обычным пользователям.

## Миграции

Приложение автоматически выполняет миграции перед запуском HTTP-сервера. В проекте 12 версий миграций:

- `000001_init_schema` — исходная схема;
- `000002_seed_admin` — безопасный bootstrap-marker без известного пароля;
- `000003_hardening` — JWT token version, роли, FK тренеров, orders и ограничения;
- `000004_ai_rag` — pgvector, документы, чанки, диалоги и AI-сообщения;
- `000005_ai_message_sources` — сохранение RAG-источников в истории;
- `000006_training_subscription_link` — привязка занятия к конкретному абонементу;
- `000007_phone_canonicalization` — единый формат телефонов и canonical email;
- `000008_purchase_snapshots` — исторические название/цена покупки;
- `000009_schema_invariants` — legacy `pending` training cleanup, обязательные ownership FK и дополнительные DB-инварианты;
- `000010_crm_expansion` — заморозка абонементов, прогресс, staff notes, follow-up tasks, уведомления и audit log;
- `000011_account_access` — pending activation state и одноразовые activation/password-reset tokens;
- `000012_review_fixes` — тренер в заявке на тренировку, пол в заявке на регистрацию, пересчёт даты последнего посещения по завершённым тренировкам. У старых заявок новые поля остаются пустыми; менеджер уточняет их при одобрении.

Перед применением к существующей важной БД обязательно сделайте backup. Миграции намеренно прекращают выполнение с понятной ошибкой, если встречают legacy-данные, которые невозможно безопасно исправить автоматически (например, NULL owner или неоднозначные дубли телефонов).

## Безопасность и роли

- manager не может создать/назначить admin;
- manager может менять статус только задач, назначенных ему; admin — любых задач;
- client видит только свои занятия, заявки, платежи, заказы и AI-диалоги;
- самостоятельное пополнение баланса клиентом удалено;
- login ограничен 10 попытками/минуту/IP, публичная заявка — 5/час/IP;
- при reverse proxy дополнительно настройте rate limiting на доверенном ingress;
- JWT жёстко ограничен HS256 и issuer, имеет expiration и `token_version`;
- пользователь и актуальная роль перечитываются из БД на каждом защищённом запросе;
- смена пароля/активности отзывает старые JWT;
- CORS использует allowlist из `CORS_ALLOWED_ORIGIN`;
- внутренние ошибки PostgreSQL не выдаются клиенту;
- body ограничен 1 MiB, неизвестные JSON-поля отклоняются.

## Расписание и абонементы

Новое/изменённое занятие:

- должно принадлежать активному клиенту;
- резервирует конкретный абонемент, который покрывает интервал занятия;
- не может использовать абонемент другого клиента;
- учитывает уже запланированные занятия при подсчёте оставшихся посещений;
- продолжает резервировать посещение, пока статус `scheduled`, даже если время занятия уже прошло;
- проверяется на пересечения у клиента и тренера;
- при `completed` списывает сессию именно с зарезервированного абонемента и увеличивает visits в одной транзакции.
- клиент может отменить своё `scheduled` занятие не позднее чем за 2 часа до начала; при этом занятие не списывается;
- замороженный абонемент нельзя использовать для новых/завершаемых тренировок;
- заморозка через CRM блокируется, пока на абонементе есть запланированные тренировки.

## Финансы и история покупок

Изменение баланса, payment и покупка выполняются атомарно в PostgreSQL-транзакциях. Денежные значения перед записью переводятся в целые копейки, а PostgreSQL хранит `NUMERIC(12,2)`.

Абонементы и sports orders сохраняют snapshot названия продукта, а абонемент также snapshot цены покупки. Позднее редактирование товара администратором не переписывает исторические покупки.

## Bootstrap администратора

Используются:

```env
ADMIN_EMAIL=admin@gmail.com
ADMIN_PASSWORD=...
```

Известного admin-пароля по умолчанию нет. `ADMIN_PASSWORD` применяется для первого bootstrap/создания и не перезаписывает нормальный пароль на каждом рестарте.

При первом запуске с собственным `ADMIN_EMAIL` используется существующая заготовка администратора из миграции. Повторного пользователя с тем же служебным телефоном не создаётся. Последующая смена email администратора в профиле сохраняется при рестарте.

### Визуальное обновление

Frontend сохранил исходную тёмно-синюю SFEDU стилистику, но получил более аккуратную визуальную иерархию: современные navy/glass surfaces, мягкие тени и границы, более выразительные primary actions, улучшенные таблицы/календарь/карточки, явный keyboard focus, responsive tweaks и `prefers-reduced-motion`. ### Назначение тренеров и фотографии

Администратор открывает **Тренерский состав → Добавить тренера**, выбирает существующего активного пользователя, специализацию и опыт. После назначения тренер автоматически появляется в выборе **Расписание → Добавить тренировку → С тренером**. Если тренеру нужен доступ к служебной части CRM, его пользователь должен иметь соответствующую роль (например, менеджер).

Фото можно выбрать прямо с компьютера. Исходный файл в backend не отправляется: браузер сначала обрезает его до квадратного превью, уменьшает максимум до 320×320 и сжимает в WebP (JPEG используется только как fallback). Backend принимает не более 96 KiB и хранит файл в `data/uploads/trainers/`, а в PostgreSQL остаётся только короткий путь к изображению. При замене или удалении старый управляемый файл очищается автоматически.
